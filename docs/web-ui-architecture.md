# ARC Agent — Web UI Architecture

> **ARC** = Automatic Reference Counting. The web UI follows the same philosophy as the agent itself: deterministic, predictable, and efficient. A declarative Swift DSL generates the entire web interface — HTML, CSS, and JavaScript — from Swift code, with zero hand-written web technology and zero external dependencies.

## Elevator Pitch

A declarative, Swift-native web UI framework — built into ARC Agent as a first-class subsystem — that generates a complete, world-class web interface from SwiftUI-style view descriptions. Every pixel of HTML, every CSS rule, and every line of JavaScript is produced by Swift code. The entire UI is embedded in the single binary. No npm, no bundler, no hand-written web code.

## Guiding Principles

1. **Swift-native, always.** The UI is described in Swift, rendered from Swift, and served by Swift. The browser receives the output of Swift code — it never hosts a separate application. There is no JavaScript framework, no build pipeline, no package.json.

2. **Declarative composition.** Views describe *what* they should look like, not *how* to build it. The rendering pipeline transforms the view tree into HTML. This is the same mental model as SwiftUI, applied to web output.

3. **Protocols first, structs second, macros last.** Every abstraction starts as a protocol. Concrete structs conform to protocols; protocols never depend on concrete types. Extensions reduce redundant code. Only after the protocol and struct design proves unwieldy in practice do we introduce a macro to compress the syntax. This ordering is not optional — macros that paper over a bad protocol design hide the problem, not fix it.

4. **Compile-time knowledge is the default, not the optimization.** The view tree structure, CSS rules, and JS runtime are all knowable at compile time. Views are structs — stack-allocated, inlineable. `render()` is a pure function the compiler can specialize. The `#HTMLView` macro is deferred until the runtime cost of string building is measured and proven to matter.

5. **The view tree is ephemeral.** Views are value types — they are constructed per-request, rendered once, and discarded. No mutable shared state on views. State lives in actors (session agents, WebSocket handlers) and flows into views as data.

6. **JavaScript is a static asset, not a generated artifact.** The JS runtime is ~45 lines of vanilla, dependency-free JavaScript, embedded in the binary as a Swift `let` constant. It is not generated by template functions, not produced by string interpolation, not the output of a code generator. It is a static string that the compiler embeds verbatim. Markdown rendering and syntax highlighting happen server-side in Swift — the JS runtime does not need a markdown parser or syntax highlighter.

7. **Single binary, single request.** The entire web UI is a static HTML document with embedded CSS and JS, served from the Hummingbird HTTP server already in the project. No separate asset pipeline, no CDN, no external resources. One request loads the complete application.

8. **World-class means invisible infrastructure.** The user should never think about "how the web UI works." It should look, feel, and perform like a native application. The underlying mechanism — Swift generating HTML — is an implementation detail, not a user-facing constraint.

## The Law of the Land

HEAR YE, HEAR YE. In this beautiful subsystem, of which we are so proud, there shall be a law of the land, of which all agents and humans alike shall abide unconditionally at all times. THE LAW OF THE LAND IS SIMPLE, AND AS FOLLOWS:

## Design Order

The web UI subsystem follows a strict three-step design order, mirroring the core agent's "protocols first, macros last" philosophy with an additional zeroth concern:

### Step 0: Optimize for Compile-Time Knowledge

Before writing a single line of protocol or struct code, every design decision is evaluated against one question: *can the compiler know this at build time?*

- **Views are structs** — stack-allocated, inlineable, no heap allocation for the view tree
- **CSS is static data** — `let` constants in a design system enum, not accumulated at runtime
- **JS is a static string** — a `let` constant in a Swift enum, compiled into the binary verbatim
- **`render()` is a pure function** — the compiler can inline and specialize the call chain
- **The view tree structure is knowable** — even with `[any View]` for composition, each concrete view type is resolved at compile time

The existential container overhead of `[any View]` is real but negligible for a chat UI's view tree depth (tens of nodes, not thousands). We start with `[any View]`, measure, and only complicate the type system if the numbers say we must.

### Step 1: Design Core Protocols

Every abstraction starts as a protocol. Protocols are the contract — they define what a view *is*, not how it's built. The protocol hierarchy is minimal: exactly as many protocols as there are distinct abstractions, no more.

### Step 2: Build Structs Around Protocols

Concrete types conform to protocols. Extensions on protocols provide default implementations and modifier methods. Protocols never depend on concrete types — the dependency arrow points from structs to protocols, never the reverse.

### Step 3: Add Macros for Ergonomics

Only after the protocol and struct design is proven do we consider macros. The macro compresses syntax that is technically correct but not beautifully ergonomic. The `#HTMLView` macro (compile-time HTML generation) is the prime candidate — deferred until the runtime cost is measured and proven to matter.

## Instance Relationships

A critical architectural property that must be clear at every level: which components are **singletons** (1 instance per process), which are **N instances** (per-session, per-connection), and which are **per-request** (ephemeral). The view tree is unique in that it is entirely ephemeral — constructed, rendered, and discarded within a single HTTP request.

```
Legend:
  [1]  = exactly 1 instance per process (singleton)
  [N]  = N instances, one per active WebSocket connection
  [*]  = unbounded (per-request, ephemeral)
```

### Heap Reference Rules

| Component | Count | Heap | Lifecycle |
|---|---|---|---|
| `View tree` | * | struct (no heap) | Per-request (ephemeral) |
| `HTMLDocument` | * | struct (no heap) | Per-request (ephemeral) |
| `WebSocketHandler` | N | actor | Connection lifetime |
| `AppStyles` | 1 | enum (no heap) | Process lifetime (no instances) |
| `Scripts` | 1 | enum (no heap) | Process lifetime (no instances) |

### Key Relationships

- **1 HTTP request → 1 view tree.** Each request to `GET /ui` constructs a fresh view tree from the current application state and renders it to a complete HTML document. The view tree is a value type — no caching, no mutation, no shared references.

- **1 WebSocket connection → 1 WebSocketHandler actor.** Each browser tab opens one WebSocket connection. The handler is an actor that serializes incoming messages and outgoing updates. It holds a reference to the session's `SessionAgent` for dispatching user messages and receiving streaming responses.

- **N WebSocketHandlers → 1 AppStyles.** The design system is an enum with no instances. CSS rules are static `let` constants. All handlers share the same stylesheet by value.

- **N WebSocketHandlers → 1 Scripts.** The JS runtime is an enum with no instances. A single `let` constant holds the complete JavaScript. All handlers inline the same script.

- **1 WebSocketHandler → 1 AsyncStream.** Each handler owns an `AsyncStream` of outgoing messages (streaming tokens, status updates, errors). The stream feeds into the WebSocket outbound channel.

## Subsystem Architecture

### 1. Core Protocols [* — one per view in the tree, ephemeral]

**Purpose:** The fundamental abstractions for describing web UI components. Every visual element in the ARC Agent web interface conforms to `View`.

```swift
/// A view that renders to an HTML string.
///
/// Views are the building blocks of the ARC Agent web UI.
/// Each view produces an HTML string when rendered. Views are
/// value types — they are constructed, rendered, and discarded
/// within a single request. No mutable shared state.
///
/// `render()` is a pure function — the same view tree always
/// produces the same HTML string. No side effects, no context
/// parameter, no mutable state passed through the tree.
///
/// ## Concurrency
///
/// `View` conforms to `Sendable`. Views are value types with no
/// mutable state. The rendering pipeline is a pure function:
/// view tree → HTML string.
public protocol View: Sendable {
    /// Render this view to an HTML string.
    func render() -> String
}
```

```swift
/// A modifier that wraps rendered content with additional
/// HTML attributes or inline styles.
///
/// Modifiers are applied via methods on `View`:
///
/// ```swift
/// Text("Hello")
///     .font(size: 16, weight: "600")
///     .foregroundColor("#e0e0e0")
/// ```
///
/// Each modifier returns a `ModifiedView<Self>` that preserves
/// the concrete type of the wrapped view through the chain.
public protocol ViewModifier: Sendable {
    /// Apply this modifier to rendered HTML content.
    func apply(to html: String) -> String
}
```

**Key design decisions:**
- `View` has a single method: `render() -> String`. No context parameter, no side effects. The simplest possible abstraction.
- `ViewModifier` is a separate protocol so modifiers can be composed and reused independently of any specific view.
- Both protocols are `Sendable`. Conformance is automatic for structs with no mutable state.
- The protocol hierarchy is flat — two protocols, each with an obvious job.

### 2. Concrete View Types [* — one per element in the tree]

**Text — inline content:**

```swift
public struct Text: View {
    public let content: String
    public init(_ content: String) { self.content = content }
    public func render() -> String { htmlEscape(content) }
}
```

**Div — generic block container:**

```swift
public struct Div: View {
    public let id: String?
    public let `class`: String?
    public let children: [any View]

    public init(
        id: String? = nil,
        class: String? = nil,
        @ViewBuilder content: () -> [any View]
    ) {
        self.id = id
        self.class = `class`
        self.children = content()
    }

    public func render() -> String {
        var html = "<div"
        if let id { html += " id=\"\(id)\"" }
        if let `class` { html += " class=\"\(`class`)\"" }
        html += ">"
        for child in children { html += child.render() }
        html += "</div>"
        return html
    }
}
```

**VStack — vertical layout:**

```swift
public struct VStack: View {
    public let alignment: HorizontalAlignment
    public let spacing: Int
    public let children: [any View]

    public init(
        alignment: HorizontalAlignment = .leading,
        spacing: Int = 8,
        @ViewBuilder content: () -> [any View]
    ) {
        self.alignment = alignment
        self.spacing = spacing
        self.children = content()
    }

    public func render() -> String {
        let alignClass = "align-\(alignment.cssValue)"
        return """
        <div class="vstack spacing-\(spacing) \(alignClass)">
        \(children.map { $0.render() }.joined())
        </div>
        """
    }
}
```

### 3. Modifier System [* — one per styled view, ephemeral]

The `ModifiedView` struct preserves the concrete type of the wrapped view through the modifier chain:

```swift
public struct ModifiedView<Content: View>: View {
    public let content: Content
    public let modifier: any ViewModifier

    public func render() -> String {
        modifier.apply(to: content.render())
    }
}
```

**Concrete modifiers:**

```swift
public struct InlineStyle: ViewModifier {
    public let property: String
    public let value: String
    public func apply(to html: String) -> String {
        "<span style=\"\(property): \(value);\">\(html)</span>"
    }
}

public struct HTMLAttribute: ViewModifier {
    public let key: String
    public let value: String
    public func apply(to html: String) -> String {
        "<span \(key)=\"\(value)\">\(html)</span>"
    }
}
```

**Modifier composition:**

```swift
public struct ComposedModifier<First: ViewModifier, Second: ViewModifier>: ViewModifier {
    public let first: First
    public let second: Second
    public func apply(to html: String) -> String {
        second.apply(to: first.apply(to: html))
    }
}
```

### 4. CSS Design System [1 — static data, no instances]

CSS is defined in a central design system enum. Views reference class names defined here. No CSS is accumulated during rendering — it is static data, knowable at compile time.

```swift
public struct CSSRule: Sendable {
    public let selector: String
    public let declarations: [(String, String)]
    public init(_ selector: String, _ declarations: [(String, String)]) {
        self.selector = selector
        self.declarations = declarations
    }
}

public struct CSSStylesheet: Sendable {
    public let rules: [CSSRule]
    public init(_ rules: [CSSRule]) { self.rules = rules }
    public func render() -> String {
        rules.map { rule in
            "\(rule.selector) {\n"
            + rule.declarations.map { "  \($0.0): \($0.1);" }.joined(separator: "\n")
            + "\n}"
        }.joined(separator: "\n\n")
    }
}
```

The design system is an enum with no cases — a namespace for static `let` constants:

```swift
public enum AppStyles {
    public static let theme = CSSRule(":root", [
        ("--bg-primary", "#0d1117"),
        ("--bg-secondary", "#161b22"),
        ("--text-primary", "#e6edf3"),
        ("--accent", "#58a6ff"),
        ("--border", "#30363d"),
    ])
    public static let reset = CSSRule("*", [
        ("margin", "0"), ("padding", "0"), ("box-sizing", "border-box"),
    ])
    public static let body = CSSRule("body", [
        ("font-family", "-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif"),
        ("background-color", "var(--bg-primary)"),
        ("color", "var(--text-primary)"),
    ])
    // ... ~20 more rules for layout, chat bubbles, input bar, markdown

    public static let all: [CSSRule] = [theme, reset, body, /* ... */]
}
```

### 5. JavaScript Runtime [1 — static string, compiled into binary]

The JS runtime is a single `let` constant in a Swift enum. It is not generated, not templated, not produced by string interpolation. It is a static asset — no different from an embedded font or image.

```swift
/// The JavaScript runtime for the ARC Agent web UI.
///
/// ~45 lines of vanilla JS. Compiled into the binary as a static string.
/// Inlined in the HTML via <script> tag. No external files, no build step.
///
/// ## Capabilities
/// - WebSocket connection management
/// - DOM patching for streaming token updates
/// - Auto-scroll on new content
/// - Enter-to-send keyboard handler
///
/// ## What is NOT here (server-side in Swift)
/// - Markdown rendering
/// - Syntax highlighting
/// - State management
public enum Scripts {
    /// The complete JavaScript runtime, verbatim.
    public static let runtime = """
    (function() {
      const ws = new WebSocket('/ui/ws');
      ws.onmessage = function(e) {
        const m = JSON.parse(e.data);
        switch(m.type) {
          case 'token':    appendToken(m.text); break;
          case 'message':  appendMessage(m.html); break;
          case 'status':   document.getElementById('status').textContent = m.text; break;
        }
      };
      ws.onopen  = function() { document.getElementById('conn').className = 'on'; };
      ws.onclose = function() { document.getElementById('conn').className = 'off'; };
      window.__ws = ws;
    })();
    function appendToken(t) {
      const c = document.getElementById('messages');
      let l = c.lastElementChild;
      if (!l || !l.classList.contains('streaming')) {
        l = document.createElement('div');
        l.className = 'message-bubble assistant streaming';
        c.appendChild(l);
      }
      l.textContent += t;
      window.scrollTo(0, document.body.scrollHeight);
    }
    function appendMessage(html) {
      const c = document.getElementById('messages');
      const el = document.createElement('div');
      el.className = 'message-bubble';
      el.innerHTML = html;
      c.appendChild(el);
      window.scrollTo(0, document.body.scrollHeight);
    }
    document.addEventListener('keydown', function(e) {
      if (e.key === 'Enter' && !e.shiftKey) {
        e.preventDefault();
        const input = document.getElementById('message-input');
        if (input.value.trim()) {
          window.__ws.send(JSON.stringify({type:'message', text: input.value}));
          input.value = '';
        }
      }
    });
    """
}
```

### 9. WebSocket Handler [N — one per active connection]

```swift
actor WebSocketHandler {
    let sessionID: String
    private let agent: SessionAgent
    private var outgoingStream: AsyncStream<OutgoingMessage>.Continuation?

    func handleInbound(_ text: String) async {
        guard let data = text.data(using: .utf8),
              let command = try? JSONDecoder().decode(WSCommand.self, from: data)
        else { return }

        switch command.type {
        case .message:
            let responseStream = await agent.processMessage(command.text)
            for try await delta in responseStream {
                let payload = try JSONEncoder().encode(WSOutgoing.token(delta))
                try await sendToWebSocket(payload)
            }
        case .ping:
            try await sendToWebSocket(Data("{\"type\":\"pong\"}".utf8))
        }
    }
}
```

## Build Order & Milestones

### Phase W1: Core Protocols & Primitive Views (the skeleton)

- [ ] **View protocol** — `protocol View: Sendable { func render() -> String }`
- [ ] **ViewModifier protocol** — `protocol ViewModifier: Sendable { func apply(to:) -> String }`
- [ ] **ModifiedView** — generic struct preserving concrete type through modifier chain
- [ ] **Concrete modifiers** — `InlineStyle`, `HTMLAttribute`, `ComposedModifier`
- [ ] **ViewBuilder** — `@resultBuilder` with full build method support
- [ ] **Primitive views** — `Text`, `Div`, `Span`, `VStack`, `HStack`, `Spacer`
- [ ] **Modifier methods** — `.backgroundColor()`, `.foregroundColor()`, `.font()`, `.padding()`, `.id()`, `.class()`
- [ ] **HTML escaping** — `htmlEscape()` utility function
- [ ] **Unit tests** — verify each primitive view produces correct HTML; verify modifier composition

**Deliverable:** A working Swift DSL that produces valid HTML from declarative view descriptions. No CSS, no JS, no server integration — just the core rendering pipeline.

### Phase W2: CSS Design System & Document Assembly (the skin)

- [ ] **CSSRule** — struct with selector and declarations
- [ ] **CSSStylesheet** — collection of rules with `render()` method
- [ ] **AppStyles** — design system enum with theme, layout, chat, markdown, and input styles
- [ ] **HTMLDocument** — struct that assembles body + styles + scripts into a complete document
- [ ] **Hummingbird route** — `GET /ui` renders the view tree and returns HTML
- [ ] **Unit tests** — verify CSS rendering; verify document assembly

**Deliverable:** A served web page with styled content, accessible at `http://localhost:8080/ui`.

### Phase W3: JavaScript Runtime (the nerves)

- [ ] **Scripts.runtime** — ~45 line JS `let` constant (WebSocket client, DOM patcher, input handler)
- [ ] **WebSocket handler** — `WebSocketHandler` actor with message parsing and response streaming
- [ ] **Hummingbird WebSocket route** — `WS /ui/ws` creates handler, wires to session

## Key Architectural Decisions (Resolved)

### 1. `render() -> String` over `render(_ context:) -> String`

The rendering pipeline is a pure function — view tree in, HTML string out. No context parameter, no side effects, no mutable state threaded through the tree. CSS and JS are separate concerns, produced independently.

### 2. Central CSS design system over per-view CSS

All CSS rules are defined in a single `AppStyles` enum as static `let` constants. Views reference class names defined there. The stylesheet is produced once and cached. Finding and modifying styles is trivial — they're all in one file.

### 3. Server-side markdown and syntax highlighting over client-side

Markdown rendering and syntax highlighting happen in Swift, before the response reaches the browser. The JS runtime receives pre-rendered HTML. This eliminates the need for a JS markdown library or syntax highlighter.

### 4. `ModifiedView<Content: View>` over existential `any View` modifiers

The modifier chain preserves the concrete type of the wrapped view through the generic `Content` parameter. This enables the compiler to specialize through the chain.

### 5. Inline CSS/JS over external files

All CSS and JavaScript is inlined in the HTML document (`<style>` and `<script>` tags). This eliminates the need for separate file serving, caching headers, and asset pipeline logic.

### 6. JS as a static `let` constant over generated JS

The JavaScript runtime is a single `let` string constant in a Swift enum. It is not generated by template functions, not produced by string interpolation, not the output of a code generator. It is a static asset compiled into the binary verbatim. This eliminates an entire class of bugs (string interpolation errors, escaping mistakes, template syntax issues) and makes the JS trivially auditable — open the file, read the JS.

### 7. WebSocket over SSE for streaming

WebSockets provide bidirectional communication. SSE (Server-Sent Events) is unidirectional and would require a separate mechanism for client-to-server messages. WebSockets are well-supported in Hummingbird and all modern browsers.

### 8. CSS custom properties over a preprocessor

Theming is implemented with CSS custom properties (variables) on `:root`. Dark and light themes are two sets of `:root` variable definitions.
